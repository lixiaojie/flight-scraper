# 城市选择逻辑优化说明

## 📋 问题背景

通过 Appium Inspector 检查空铁联运页面发现：
- UiSelector 无法提供有效的甄别信息来区分出发和到达城市
- 页面结构中没有明确的 resource-id 或 content-desc 标识

## ✅ 解决方案

根据 Appium Inspector 的发现，实现了两种新的识别策略：

### 策略0：使用 UiSelector 缩小范围（最高优先级）

在指定的 View 容器内查找城市元素：
- 容器：`new UiSelector().className("android.view.View").instance(13)`
- 规则：第一个城市 = 出发，第二个城市 = 到达
- 两个城市中间相隔 `instance(14)`

**实现逻辑**：
1. 在 `View.instance(13)` 容器内查找所有 `TextView` 元素
2. 筛选出城市元素（2-4个中文字符）
3. 按 x 坐标排序（从左到右）
4. 第一个城市 = 出发，第二个城市 = 到达

### 策略0.5：按顺序提取（次优先级）

如果策略0失败，回退到按顺序提取：
- 查找页面中所有符合条件的城市元素（2-4个中文字符，y坐标在500-800范围内）
- 按 x 坐标排序（从左到右）
- 第一个城市 = 出发，第二个城市 = 到达

### 原有策略（保留作为后备）

如果新策略都失败，仍然保留原有的识别策略：
- 策略1：通过 resource-id、content-desc 或文本标签识别
- 策略2：通过 resource-id 或 content-desc 直接查找
- 策略3：通过城市名查找
- 策略4：通过位置筛选（x坐标）

## 🔧 代码修改

### 修改文件
- `scripts/city_selection.py` - `find_city_element` 函数

### 新增逻辑
1. **策略0**：在函数开头添加，使用 UiSelector 缩小范围
2. **策略0.5**：紧接着策略0，按顺序提取城市元素
3. **保留原有策略**：作为后备方案

## 🎯 优势

1. **更精确**：优先使用 UiSelector 缩小范围，减少误识别
2. **更可靠**：按顺序提取作为后备，即使容器结构变化也能工作
3. **向后兼容**：保留所有原有策略，确保现有功能不受影响
4. **易于调试**：详细的日志输出，便于排查问题

## 🔍 调试建议

如果城市选择仍然失败，可以：

1. **检查日志**：查看哪个策略被使用，哪个策略失败
2. **验证容器结构**：确认 `View.instance(13)` 是否仍然有效
3. **检查城市数量**：确认页面中是否确实有两个城市元素
4. **验证排序**：确认按 x 坐标排序后，第一个确实是出发城市
